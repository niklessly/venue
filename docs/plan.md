# План разработки

## Цель проекта

Разработать Angular-приложение для бронирования переговорных комнат в офисе с учётом вместимости, оборудования и конфликтов по времени. Приложение должно помогать сотрудникам быстро находить подходящую комнату, создавать бронирования, управлять ими и отслеживать загрузку помещений.

Продукт ориентирован на офисных сотрудников и администраторов компании. Пользователь должен видеть доступные комнаты, фильтровать их по параметрам, создавать и изменять бронирования, а также получать представление о статистике использования помещений.

## Пользовательские сценарии

1. Сотрудник входит в систему, находит подходящую переговорную по времени, вместимости и оборудованию и создаёт бронирование без конфликта с уже существующими встречами.
2. Сотрудник просматривает свои бронирования, переносит или отменяет встречу, при необходимости создаёт повторяющееся бронирование.
3. Администратор или офис-менеджер смотрит статистику загрузки комнат, проверяет оборудование в комнатах и управляет данными о помещениях.

## Этапы разработки

| Срок            | Задача                                                                                                                                                                                              |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| До конца апреля | Сделать основу проекта: подготовить маршруты, общую структуру папок, первые страницы и формы, а также заполнить `docs/plan.md` и `docs/ux.md`.                                                      |
| До конца мая    | Собрать рабочую версию: подключить mock-API, сделать авторизацию, защиту маршрутов, состояние приложения, CRUD для комнат и бронирований, поиск, фильтры, сортировку и обработку загрузки и ошибок. |
| За начало июня  | Довести проект до сдачи: проверить адаптивность, добавить тесты, настроить CI/CD, сделать деплой, проверить Lighthouse и обновить README.                                                           |

## Риски

1. Сложные проверки времени и повторяющихся бронирований — вынести эту логику в отдельный сервис и сразу покрыть её тестами.
2. Можно запутаться в структуре проекта — заранее разделить код на `core`, `shared` и `features` и не смешивать бизнес-логику с UI.
3. Не хватит времени на тесты и деплой — не откладывать CI/CD и проверку Lighthouse на самый конец.
